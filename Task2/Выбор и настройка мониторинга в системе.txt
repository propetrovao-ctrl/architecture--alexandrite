Мотивация

Сейчас система подключена только к Яндекс Метрике, которая показывает события на фронтенде. Но после открытия API для партнеров появились проблемы
Потеря заказов через RabbitMQ
Тормоза в MES
Проблемы при большой нагрузке

Яндекс Метрика не показывает состояние внутренних сервисов (API, базы данных, очереди). Нужен полноценный мониторинг, чтобы
   Видеть проблемы до того как о них сообщат клиенты
   Быстро находить причины сбоев
   Планировать масштабирование
   Снизить потери от потерянных контрактов


Обоснование для бизнеса

Почему мониторинг критически важен

1. Защита от потери клиентов и контрактов
Сейчас мы узнаем о проблемах только когда клиенты жалуются. За это время уже потеряны заказы и репутация. Мониторинг позволит обнаруживать проблемы за 5-10 минут до того, как они станут критичными. Это предотвратит потерю крупных контрактов, как это уже произошло несколько раз

2. Снижение времени простоя системы
Без мониторинга поиск причины проблемы занимает часы. С мониторингом команда видит, где именно проблема (API, база данных, очередь), и может исправить её за 15-30 минут. Это означает меньше потерянных заказов и меньше недовольных клиентов

3. Оптимизация расходов на инфраструктуру
Сейчас мы не знаем, когда нужно масштабировать систему. Либо масштабируем слишком рано (лишние расходы), либо слишком поздно (падение системы). Мониторинг покажет реальную нагрузку и позволит планировать масштабирование заранее, экономя деньги

4. Повышение производительности команды
Разработчики тратят много времени на поиск проблем "вслепую". С мониторингом они сразу видят проблему и могут её исправить. Это освобождает время для разработки новых функций вместо постоянного тушения пожаров

5. Улучшение SLA для партнеров
Партнеры, использующие наш API, требуют стабильности. Мониторинг позволит гарантировать определенный уровень доступности и быстро реагировать на проблемы. Это поможет сохранить и привлечь новых партнеров

Ожидаемый эффект
   Сокращение потерь от потерянных контрактов на 70-80%
   Уменьшение времени простоя системы с часов до минут
   Снижение времени на диагностику проблем с 2-4 часов до 15-30 минут
   Возможность планировать масштабирование и экономить на инфраструктуре


Выбор подхода к мониторингу

Для разных частей системы используем разные подходы

1. API-сервисы (Shop API, CRM API, MES API) метод RED
RED подходит для API, потому что отслеживает
   Rate сколько запросов в секунду
   Errors сколько ошибок
   Duration сколько времени занимает обработка

2. Инфраструктура (базы данных, RabbitMQ, S3) метод USE
USE подходит для ресурсов
   Utilization использование CPU, памяти
   Saturation насколько система загружена
   Errors ошибки в работе

3. Общий мониторинг Четыре золотых сигнала
Для общей картины используем
   Задержка (Latency)
   Трафик (Traffic)
   Ошибки (Errors)
   Насыщенность (Saturation)


Метрики для отслеживания

Выбранные метрики покрывают критические точки системы, которые напрямую влияют на бизнес-результаты. Каждая метрика помогает предотвратить конкретные проблемы, которые уже приводили к потерям контрактов и недовольству клиентов

1. Метрики RabbitMQ

Number of message in flight in RabbitMQ
Зачем. Показывает сообщения в обработке. Помогает найти задержки
Бизнес-обоснование. Потеря заказов через RabbitMQ одна из главных проблем. Эта метрика покажет, когда очередь переполняется и заказы могут теряться. Позволит предотвратить потерю заказов до того, как клиенты начнут жаловаться
Ярлыки: queue_name, consumer_tag
Порог > 1000 сообщений более 5 минут


2. Метрики производительности API (RED)

Number of requests (RPS) for API (Shop API, CRM API, MES API)
Зачем. Rate частота запросов. Показывает нагрузку на API
Бизнес-обоснование. Позволяет видеть рост нагрузки заранее и планировать масштабирование до того, как система упадет. Это критично для API-партнеров если API недоступен, они теряют заказы и могут разорвать контракт
Ярлыки api_name (shop/crm/mes), endpoint, method
Порог > 1000 RPS для Shop API, > 500 для CRM API, > 200 для MES API в течение 10 минут

Response time (latency) for API
Зачем. Duration длительность обработки запросов. Высокая задержка = недовольные клиенты
Бизнес-обоснование. Медленная работа системы приводит к оттоку клиентов. Клиенты уходят к конкурентам, если сайт тормозит. Мониторинг задержек позволит находить проблемы производительности до того, как клиенты начнут жаловаться
Ярлыки api_name, endpoint, method, status_code
Порог p95 > 2 секунды для Shop/CRM API, > 3 секунды для MES API (кроме расчета стоимости)

Number of HTTP 500 for API
Зачем. Errors ошибки при обработке запросов. Критично для стабильности
Бизнес-обоснование. Ошибки сервера означают, что клиенты не могут оформить заказы. Каждая ошибка потенциально потерянный заказ. Раннее обнаружение ошибок позволит исправить их до массового влияния на клиентов
Ярлыки: api_name, endpoint, method, error_type
Порог > 10 ошибок в минуту или error rate > 1%


3. Системные метрики (USE)

CPU % for API (Shop API, CRM API, MES API)
Зачем. Utilization загрузка процессора. Высокая загрузка = проблемы
Бизнес-обоснование. Высокая загрузка CPU означает, что система работает на пределе и может упасть при росте нагрузки. Обнаружение проблемы заранее позволит масштабировать систему до падения, избежав простоя и потери заказов
Ярлыки api_name, instance_id
Порог > 80% в течение 5 минут

Memory Utilisation for API
Зачем. Utilization использование памяти. Утечки могут привести к падению
Бизнес-обоснование. Утечки памяти приводят к падению сервиса. Обнаружение проблемы до падения позволит перезапустить сервис в плановом режиме, а не в экстренном, когда уже потеряны заказы
Ярлыки api_name, instance_id
Порог > 85% в течение 5 минут

Number of connections for database
Зачем. Saturation количество подключений к БД. Превышение лимита = отказ
Бизнес-обоснование. Превышение лимита подключений к БД означает, что новые заказы не могут быть обработаны. Это критично для бизнеса система перестает принимать заказы. Мониторинг позволит добавить ресурсы до достижения лимита
Ярлыки db_name, instance_id, database_name
Порог > 80% от максимума

Number of dead-letter-exchange letters in RabbitMQ
Зачем. Errors сообщения, которые не удалось обработать (USE: Errors)
Бизнес-обоснование. Каждое сообщение в DLX это потерянный заказ. Это прямая потеря денег. Мониторинг покажет проблему сразу, как только появится первое сообщение, и позволит быстро исправить ситуацию
Ярлыки exchange_name, queue_name, reason
Порог > 0 (любое сообщение в DLX это проблема)


4. Метрики хранилища

Size of S3 storage
Зачем. Использование хранилища 3D-файлов. Превышение = отказ загрузки
Ярлыки bucket_name
Порог > 80% от выделенного объема

Size of database instance
Зачем. Размер базы данных. Быстрый рост = проблемы
Ярлыки db_name, instance_id, database_name
Порог > 80% от максимума


5. Метрики "Четыре золотых сигнала"

Response time (latency) for API
Зачем. Latency задержка отклика системы. Показывает время обработки запросов
Ярлыки api_name, endpoint, method, status_code
Порог p95 > 2 секунды для Shop/CRM API, > 3 секунды для MES API

Number of requests (RPS) for API
Зачем. Traffic трафик системы. Показывает нагрузку на API
Ярлыки api_name, endpoint, method
Порог > 1000 RPS для Shop API, > 500 для CRM API, > 200 для MES API

Number of HTTP 500 for API
Зачем. Errors ошибки в системе. Критично для стабильности
Ярлыки api_name, endpoint, method, error_type
Порог > 10 ошибок в минуту или error rate > 1%

Number of message in flight in RabbitMQ
Зачем. Saturation насыщенность системы. Показывает загрузку очереди
Ярлыки queue_name, consumer_tag
Порог > 1000 сообщений более 5 минут

6. Бизнес-метрики

Время расчета стоимости заказа (MES API)
Зачем. Производительность расчета (может занимать до 30 минут)
Бизнес-обоснование. Долгий расчет стоимости заказа означает, что клиент ждет и может уйти к конкурентам. Мониторинг покажет, когда расчеты замедляются, и позволит оптимизировать процесс или добавить ресурсы
Ярлыки order_id, polygon_count, complexity_level
Порог > 30 минут для одного расчета

Количество заказов в статусе "ожидает расчета"
Зачем. Очередь заказов, ожидающих расчета
Бизнес-обоснование. Большая очередь означает, что система не справляется с нагрузкой. Клиенты ждут расчета стоимости и могут отменить заказ. Мониторинг покажет проблему до того, как очередь станет критической
Ярлыки status
Порог > 100 заказов в очереди более 1 часа

Показатели насыщенности

1. Пороговые значения


API-сервисы
CPU > 80% в течение 5 минут
Memory > 85% в течение 5 минут
Response time p95 > 2 секунды (Shop/CRM), > 3 секунды (MES)

Базы данных
CPU > 75% в течение 5 минут
Memory > 90% в течение 5 минут
Подключения > 80% от максимума
Размер БД > 80% от максимума

RabbitMQ
Очередь > 1000 сообщений более 5 минут
Сообщений в обработке > 500 более 10 минут
Memory > 85% в течение 5 минут

S3
Использование > 80% от выделенного объема

2. Действия при превышении порогов


API-сервисы
1. Создать тикет
2. Уведомить команду
3. Если > 10 минут уведомить DevOps
4. Подготовить план масштабирования

Базы данных
1. Создать тикет с приоритетом "High"
2. Уведомить DevOps и тимлида
3. При превышении подключений добавить read-replica
4. При превышении размера запустить архивацию

RabbitMQ
1. Создать критический тикет
2. Уведомить команду
3. Проверить consumer'ы
4. Если очередь переполнена ограничить прием заказов (backpressure)
5. Добавить worker'ы при необходимости

S3
1. Создать тикет
2. Уведомить DevOps
3. Запустить очистку старых файлов
4. Рассмотреть увеличение квоты
