Системы, которые нужно покрыть трейсингом:

1. Shop API, CRM API, MES API все три API сервиса
2. RabbitMQ передача сообщений между сервисами
3. Базы данных (Shop DB, MES DB) сохранение данных
4. S3 Storage загрузка 3D-файлов

Места, где заказ может сломаться или зависнуть
Создание заказа в Shop API
Передача через RabbitMQ между сервисами
Расчет стоимости в MES API (до 30 минут)
Обновление статусов заказа
Загрузка файлов в S3


Данные для трейсинга

Обязательные данные
trace_id уникальный идентификатор для всего заказа
span_id идентификатор этапа обработки
order_id идентификатор заказа
service_name название сервиса
operation_name название операции
duration время выполнения
status статус (success, error)
error_message сообщение об ошибке

Контекстные данные
user_id, endpoint, http_method, http_status_code
message_queue, message_type (для RabbitMQ)
order_id, status (для связи с бизнес-процессом)


Мотивация

Проблемы, которые решает трейсинг

1. Потеря заказов через RabbitMQ
Сейчас непонятно где теряется заказ. Трейсинг покажет полный путь заказа через все сервисы

2. Непонятное состояние заказов
Заказы зависают. Трейсинг покажет на каком этапе заказ остановился

3. Долгий расчет стоимости
Расчет может занимать до 30 минут. Трейсинг покажет где происходит задержка

4. Проблемы с производительностью
Трейсинг поможет найти узкие места в системе

Технические метрики
   Время диагностики с 2-4 часов до 15-30 минут
   Потеря заказов снижение на 70-80%
   Время поиска проблем с дней до часов

Бизнес-метрики
   Потеря контрактов снижение на 80%
   Время обработки жалоб с часов до минут
   Удовлетворенность партнеров повышение


Предлагаемое решение

Технологии
OpenTelemetry стандарт для сбора трейсов
Jaeger для хранения и визуализации
OpenTelemetry Collector для обработки данных

Что нужно сделать

1. Добавить OpenTelemetry SDK в каждый сервис
   Shop API, CRM API: opentelemetry-java-instrumentation
   MES API: OpenTelemetry .NET SDK

2. Развернуть Jaeger
   Jaeger для хранения и визуализации трейсов
   Хранение в Elasticsearch

3. Развернуть OpenTelemetry Collector
   Прием данных от всех сервисов
   Отправка в Jaeger

4. Настроить передачу контекста
   trace_id и span_id в заголовках HTTP запросов
   trace_id и span_id в заголовках сообщений RabbitMQ
   Добавить order_id в атрибуты span


Компромиссы

1. Производительность
Трейсинг добавляет нагрузку (1-3% CPU и памяти). Можно использовать sampling трейсить только часть запросов

2. Хранение данных
Трейсы занимают место. Хранить не более 7 дней для продакшена

3. Проприетарные системы
MES API может быть сложно инструментировать. Можно добавить трейсинг только в критичных местах

4. Стоимость инфраструктуры
Jaeger с Elasticsearch требует дополнительных ресурсов. Можно начать с упрощенной версии

5. Обучение команды
Нужно время на обучение работе с Jaeger. Это окупится экономией времени на диагностику


Безопасность

Меры безопасности

1. Доступ к Jaeger UI
   Аутентификация через OAuth или LDAP
   Авторизация по ролям только "Поддержка", "DevOps", "Разработчик"
   HTTPS для всех соединений
   Доступ только из внутренней сети

2. Защита данных
   Не логировать пароли, токены, персональные данные
   Маскирование персональных данных
   Шифрование при передаче (TLS)

3. Изоляция окружений
   Отдельные инстансы Jaeger для dev, release, prod
   Нет доступа из dev к prod данным


Автоматический мониторинг и алертинг

1. Анализ трейсов
   OpenTelemetry Collector анализирует трейсы
   Выявляет аномалии: долгие операции, ошибки, потерянные заказы

2. Интеграция с Prometheus
   Экспорт метрик из трейсов в Prometheus
   Метрики: потерянные заказы, время обработки, ошибки

3. Правила алертинга
   Заказ завис более 1 часа → алерт
   Расчет стоимости более 30 минут → алерт
   Сообщение в RabbitMQ не обработано более 5 минут → алерт
   Ошибка при создании заказа → критический алерт

4. Уведомления
   Алерты в мессенджер
   Критические SMS DevOps
   Создание тикетов в Jira

5. Дашборды
   Grafana с метриками из трейсинга
