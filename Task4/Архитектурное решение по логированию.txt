Системы, из которых нужно собирать логи:

1. Shop API, CRM API, MES API все три API сервиса
2. RabbitMQ передача сообщений между сервисами
3. Базы данных (Shop DB, MES DB) медленные запросы, ошибки
4. S3 Storage загрузка файлов

Список необходимых логов (уровень INFO)

Примеры логов

Shop API
Создание заказа время, customer_id, order_id, статус
Загрузка 3D-файла время, customer_id, order_id, размер файла
Отправка сообщения в RabbitMQ время, order_id, тип сообщения

CRM API
Изменение статуса заказа время, order_id, старый статус, новый статус
Получение сообщения из RabbitMQ время, order_id, тип сообщения

MES API
Расчет стоимости время, order_id, стоимость, длительность
Назначение оператора время, order_id, operator_id

RabbitMQ
Отправка/получение сообщения время, очередь, тип сообщения, order_id

Базы данных
Медленный запрос время, база данных, запрос, длительность
Ошибка транзакции время, база данных, тип ошибки


Другие уровни логирования

ERROR для ошибок
Ошибка создания заказа, расчета стоимости, обработки сообщения
Ошибка подключения к базе данных, загрузки файла

WARN для предупреждений
Долгий расчет стоимости (более 10 минут)
Медленный запрос к БД (более 1 секунды)
Большой размер файла (более 100 МБ)

DEBUG для отладки (только в dev/release)
Детали обработки запроса, параметры методов

FATAL для критических ошибок
Отказ сервиса, базы данных, RabbitMQ


Мотивация

Проблемы, которые решает логирование

1. Разбор проблем со слов клиента
Сейчас разработчики тратят часы на поиск проблемы. Логи покажут точное время, место и причину ошибки

2. Потеря заказов через RabbitMQ
Логи покажут было ли сообщение отправлено, получено и обработано

3. Долгий расчет стоимости
Логи покажут сколько времени занял расчет, на каком этапе произошла задержка

4. Проблемы с производительностью
Логи помогут найти медленные запросы и узкие места

5. Аудит действий
Логи покажут кто и когда изменил статус заказа

Технические метрики
   Время диагностики с 2-4 часов до 15-30 минут
   Время поиска потерянных заказов с часов до минут
   Процент найденных проблем с 50% до 95%

Бизнес-метрики
   Время обработки жалоб с часов до минут
   Потеря контрактов снижение на 60-70%
   Удовлетворенность клиентов повышение


Приоритеты систем для логирования

Первая очередь (критично)
1. Shop API, CRM API создание и обработка заказов
2. RabbitMQ передача сообщений между сервисами

Вторая очередь (важно)
3. MES API расчет стоимости
4. Базы данных медленные запросы, ошибки

Третья очередь (желательно)
5. S3 Storage загрузка файлов

Почему такой порядок
Shop API и CRM API точки входа заказов, здесь теряются заказы
RabbitMQ критичная точка передачи данных
MES API долгий расчет, но менее критично
Базы данных важны для производительности


Предлагаемое решение

Технологии
ELK стек (Elasticsearch, Logstash, Kibana)
Filebeat для сбора логов с серверов

Что нужно сделать

1. Установить Filebeat на каждый сервер
   Shop API, CRM API сбор логов приложений
   Базы данных, RabbitMQ сбор логов

2. Развернуть Logstash
   Прием логов от Filebeat
   Обработка и фильтрация чувствительных данных
   Отправка в Elasticsearch

3. Развернуть Elasticsearch
   Хранение логов в индексах
   Поиск по логам
   Индексы по системам и датам

4. Развернуть Kibana
   Визуализация логов
   Дашборды для каждой системы

Политика безопасности

Меры безопасности

1. Маскирование чувствительных данных
   Пароли не логировать
   Токены маскировать
   Персональные данные маскировать

2. Доступ к Kibana
   Аутентификация через OAuth или LDAP
   Авторизация по ролям только "Поддержка", "DevOps", "Разработчик"
   HTTPS для всех соединений
   Доступ только из внутренней сети

3. Изоляция окружений
   Отдельные инстансы ELK для dev, release, prod
   Нет доступа из dev к prod данным


Политика хранения

Структура индексов
Отдельный индекс для каждой системы shop-api-logs-YYYY.MM.dd, crm-api-logs-YYYY.MM.dd, mes-api-logs-YYYY.MM.dd
Отдельный индекс для RabbitMQ rabbitmq-logs-YYYY.MM.dd

Сроки хранения
Prod 30 дней для обычных логов, 90 дней для логов ошибок
Release 14 дней
Dev 7 дней

Размер индексов
Примерный размер: 1-5 ГБ на систему в день
Общий размер: 50-100 ГБ в день

Управление жизненным циклом (ILM)
Автоматическое удаление индексов после истечения срока
Перемещение старых индексов на более дешевое хранилище (через 7 дней)


Анализ логов и алертинг

1. Алертинг на основе логов

Критические алерты
Ошибка создания заказа (ERROR)
Ошибка расчета стоимости (ERROR)
Отказ сервиса (FATAL)

Предупреждения
Долгий расчет стоимости (более 10 минут)
Медленный запрос к БД (более 1 секунды) 

2. Поиск аномалий

DDoS-атака
Резкое увеличение количества запросов (с 100 до 10000 в секунду)
Много запросов с одного IP

Потеря заказов
Сообщение отправлено в RabbitMQ, но не получено
Заказ создан, но не обработан

3. Дашборды в Kibana
Количество созданных заказов по времени
Количество ошибок по типам
Время обработки запросов
Количество отправленных/полученных сообщений

4. Интеграция с системой уведомлений
Алерты в мессенджер
Критические → SMS DevOps
Создание тикетов в Jira

Сравнение технологий ELK, OpenSearch, Splunk

1. Лицензия
ELK Elastic License (бесплатно для базового функционала)
OpenSearch Apache License 2.0 (полностью открытая)
Splunk Проприетарная (очень дорого)

2. Производительность
ELK/OpenSearch Высокая производительность, достаточно для 50-100 ГБ в день
Splunk Оптимизирован для больших объемов, но требует мощное железо

3. Простота настройки
ELK Много документации, готовых решений
OpenSearch Похожая на ELK, но меньше готовых решений
Splunk Удобный интерфейс, но дорого

4. Стоимость
ELK Бесплатно для базового функционала
OpenSearch Полностью бесплатно
Splunk Очень дорого (тысячи долларов в месяц)

5. Интеграция
ELK/OpenSearch Хорошая интеграция с Yandex Cloud, Docker
Splunk Много готовых интеграций, но проприетарное

6. Поддержка и сообщество
ELK Большое сообщество, много статей
OpenSearch Растущее сообщество
Splunk Профессиональная поддержка (платно)

Итоговый выбор ELK стек

Обоснование
   Хорошая производительность для наших объемов
   Большое сообщество и документация
   Хорошая интеграция с Yandex Cloud
   Бесплатно для базового функционала
