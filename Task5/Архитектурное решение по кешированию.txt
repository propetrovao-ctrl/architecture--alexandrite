Архитектурное решение по кешированию

Анализ системы

Что нужно закешировать

1. Список заказов в MES (критично)
   Первая страница MES долго грузится
   Операторы часто запрашивают список заказов

2. Статические ресурсы (желательно)
   3D-элементы конструктора, изображения товаров

Почему именно это
Список заказов главная проблема производительности MES
Операторы постоянно обновляют страницу


Мотивация

Проблемы, которые решает кеширование

1. Медленная загрузка первой страницы MES
Операторы жалуются что страница долго грузится. Кеширование ускорит загрузку с нескольких секунд до миллисекунд

2. Высокая нагрузка на базу данных
Каждый запрос списка заказов идет в БД. Кеш снизит нагрузку на БД

3. Важность актуальности данных
Операторам важно видеть новые заказы быстро, чтобы успеть взять их в работу

Технические метрики:
- Время загрузки: с 3-5 секунд до 50-100 мс
- Нагрузка на БД: снижение на 70-80%
- Пропускная способность: увеличение в 5-10 раз

Бизнес-метрики:
- Удовлетворенность операторов: повышение
- Производительность операторов: увеличение


Предлагаемое решение

Тип кеширования Серверное кеширование

Почему серверное
Список заказов динамические данные
Клиентское кеширование не подходит для данных, требующих актуальности
Серверное кеширование позволяет гибко управлять инвалидацией

Почему Cache-Aside

1. Простота реализации
   Не требует изменений в базе данных
   Легко добавить в существующий код
   Команда может быстро обучиться

2. Устойчивость к сбоям
   Если Redis упадет система продолжит работать через БД

3. Гибкость модели данных
   Можно кешировать уже обработанные данные

Почему не другие паттерны

Write-Through
Сложнее в реализации (нужно обновлять и кеш, и БД синхронно)
Медленнее для записи (нужно ждать обновления БД)
Если Redis упадет, запись не выполнится

Write-Behind
Риск потери данных при сбое (данные в кеше, но не в БД)
Не подходит для критичных данных (статусы заказов)

Read-Through
Меньше гибкости (модель данных в кеше должна совпадать с БД)
Требует изменений в Redis или специальных библиотек

Refresh-Ahead
Избыточно для нашей задачи (нужен мониторинг и фоновые задачи)
Сложнее в реализации и поддержке

Стратегия инвалидации кеша Инвалидация по ключу + TTL

Почему инвалидация по ключу:

1. Точечное обновление данных
   При изменении статуса инвалидируется только кеш для этого заказа
   Эффективно и быстро

2. Актуальность данных
   Операторы сразу видят изменения статусов
   Важно для бизнеса

3. Простота реализации
   При изменении статуса удаляем ключ из Redis
   Ключ "orders:status:{status}" или "orders:all"

Дополнительно TTL = 5 минут
   Если забыли инвалидировать, данные обновятся автоматически
   Защита от устаревших данных

Почему не другие стратегии

Временная инвалидация (только TTL) данные могут быть устаревшими
Инвалидация на основе запросов неэффективно
Программная инвалидация похожа, но инвалидация по ключу проще



Сравнение решений

Решение 1: Cache-Aside с Redis

Описание решения и его диаграмма
   Паттерн Cache-Aside
   Redis для хранения кеша
   Инвалидация по ключу + TTL = 5 минут
   Диаграмма: Task5/caching_sequence_diagram.puml (PlantUML)

Плюсы решения
   Простота реализации и поддержки
   Устойчивость к сбоям (если Redis упадет, система работает через БД)
   Гибкость модели данных в кеше
   Быстрая инвалидация по ключу
   Команда может быстро обучиться

Минусы решения
   Возможна несогласованность данных (если забыли инвалидировать)
   Нужно управлять инвалидацией в коде
   Первый запрос всегда идет в БД (cache miss)

Решение 2: Write-Through с Redis

Описание решения и его диаграмма
   Паттерн Write-Through
   Redis для хранения кеша
   При записи обновляются и кеш и БД синхронно

Плюсы решения
   Гарантированная согласованность данных
   Не нужно инвалидировать кеш вручную
   Данные всегда актуальны

Минусы решения
   Сложнее в реализации
   Медленнее операции записи (нужно ждать обновления БД)
   Требует изменений в логике записи
   Если Redis упадет, запись не выполнится

Решение 3: HTTP-кеш (клиентское кеширование)

Описание решения и его диаграмма
   Использование заголовков Cache-Control
   Кеширование в браузере оператора
   Временная инвалидация max-age

Плюсы решения
   Не требует дополнительных серверов (Redis)
   Простота настройки (только заголовки)
   Снижает нагрузку на сервер

Минусы решения
   Не подходит для динамических данных (статусы заказов)
   Данные могут быть устаревшими
   Нет контроля над инвалидацией на сервере


Заключение

Выбираем Решение 1: Cache-Aside с Redis

   Простота реализации важна для команды
   Устойчивость к сбоям критична
   Гибкость модели данных
   Скорость записи важна
   Инвалидация по ключу обеспечивает актуальность данных

Решение 2 (Write-Through) не подходит из-за сложности и медленной записи
Решение 3 (HTTP-кеш) не подходит для динамических данных
